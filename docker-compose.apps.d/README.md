# docker-compose.apps.d/

Compose fragments that mount an application into Fact Explorer, one file per application. Each
fragment adds a bind mount to the `fact-explorer` service.

The `Makefile` passes every `*.yml` in this directory to `docker compose`, after the base file and
the dev overlay:

```make
COMPOSE_FILES := -f docker-compose.yml -f docker-compose.override.yml $(patsubst %,-f %,$(wildcard docker-compose.apps.d/*.yml))
```

A fragment's `volumes:` entries append to the ones the earlier files
already declared rather than replacing them. Every target built on `COMPOSE` picks the fragments up:
`make up`, `down`, `logs`, `build`, `ps`, and `rebuild`. `make apps` lists what is registered here
without starting anything, and `make up` runs it first.

A fragment looks like this:

```yaml
# my-application.yml, written by that application's `make up`
services:
  fact-explorer:
    volumes:
      - /Users/you/my-application:/apps-external/my-application:ro
```

Everything in this directory except this README is gitignored (see `.gitignore` in the repository
root). The fragments name absolute paths on one machine, to repositories this one does not contain.

## Relationship to `apps/`

`apps/` holds every application checkout in a single directory. Point `TAXPERT_APPS_DIR` at it and
the whole set arrives as one bind mount at `/apps`. That works when you control where the
applications live, which is the case for the [example applications
repository](https://github.com/IRS-Public/form-builder-examples).

It does not cover an application generated by `cookiecutter form-builder-template` in an arbitrary
directory, for two reasons. First, only one directory can be `TAXPERT_APPS_DIR` so an application outside it is never 
scanned. Second, a symlink in `apps/` does not survive the bind mount, so Docker carries the link, not its target. 
This means that`/apps/my-application` is a dangling symlink inside the container and discovery skips it. `apps/README.md` covers this under "Discovery".

A fragment here is a real bind mount of a real path, so neither limitation applies.

## Why the mount target is `/apps-external`

`/apps` is mounted read-only, and a mount cannot be nested inside a read-only one. Docker has to
create the mountpoint directory in the parent first, and fails with `read-only file system`.
Dropping the `:ro` would avoid that error at a cost: the `mkdir` would then land in the host's apps
directory and leave empty directories in someone's checkout.

Each fragment therefore mounts its application at `/apps-external/<app>`, a path the container
creates in its own writable layer, and Fact Explorer scans both roots.

| Piece | Where it lives | What it does |
|---|---|---|
| `FORM_BUILDER_APPS_DIR` | `docker-compose.override.yml` | Names the primary root, `/apps`. |
| `FORM_BUILDER_EXTRA_APPS_DIRS` | `docker-compose.override.yml` | Names the second root, `/apps-external`. Colon-separated. |
| `appsDirs()` | `packages/fact-explorer/scripts/build-registry.mjs` | Joins the two, primary root first. |

`discoverDescriptors()` in the same module keeps the first descriptor it sees for a given id, so the
apps directory stays authoritative when both roots contain the same application.

## Adding and removing a fragment

In normal use **you do not write one by hand.** A generated application's `make up` writes its own
fragment here by way of `scripts/register-with-taxpert.sh` in that application's repository, then
recreates the `fact-explorer` container so it re-reads this directory.

Write one by hand only for an application that predates that script. To unregister an application,
delete its fragment:

```bash
rm docker-compose.apps.d/my-application.yml
```

Keep this directory current. A fragment naming a path that no longer exists fails `docker compose
up` for the whole stack, which is the sharpest edge of this mechanism.

## Why the container has to be recreated

Fact Explorer reads the application list twice, both times at container start:

| Step | Reads | Writes |
|---|---|---|
| `npm run make-fgm` (`scripts/make-static-fgm.mjs`) | The descriptors under both roots | `public/data/apps.json`, via `buildRegistryFile()` |
| `vite.config.js` | The same descriptors, through `appsDirs()` | The dev server's proxy table |

Neither is watched. A fragment added while the stack is running has no effect until the container is
recreated, which is what the registration script does for you.
