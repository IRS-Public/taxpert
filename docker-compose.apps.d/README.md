# docker-compose.apps.d/

Compose fragments that mount an application into Fact Explorer's `/apps`, one file per application.
`make up` (and `down`, `logs`, `build`, `ps`, `rebuild`) passes every `*.yml` here to
`docker compose` after the base file and the dev overlay, so each one adds its bind mount to the
`fact-explorer` service.

```yaml
# my-application.yml — written by that app's `make up`
services:
  fact-explorer:
    volumes:
      - /Users/you/my-application:/apps-external/my-application:ro
```

Everything here except this README is gitignored: these are paths on one machine, to repositories
this one does not contain.

## Why this exists alongside `apps/`

`apps/` is the single-directory answer: put every application checkout in one place, point
`TAXPERT_APPS_DIR` at it, and the whole thing is one bind mount. That works well when you control
where the applications live — the [example applications
repository](https://github.com/IRS-Public/form-builder-examples) is already shaped that way.

It does not work for an application generated by `cookiecutter form-builder-template` wherever the
person happened to be standing. Two reasons, and the second is the one that bites:

- Only one directory can be `TAXPERT_APPS_DIR`, so an app outside it is invisible.
- A symlink in `apps/` does not survive the bind mount. Docker carries the link, not its target, so
  `/apps/my-application` inside the container is a dangling symlink and discovery skips it. This is
  the trap `apps/README.md` warns about under "Discovery".

A fragment here is a real bind mount of a real path, so neither applies.

## Why `/apps-external` and not `/apps/<app>`

Because `/apps` is mounted **read-only**, and a mount cannot be nested inside a read-only one:
Docker has to create the mountpoint directory in the parent first, and fails with
`read-only file system`. Dropping the `:ro` would work and is worse — the mkdir would then land in
the host's apps directory, littering someone's checkout with empty directories.

So each fragment mounts its app at `/apps-external/<app>`, a path the container creates in its own
writable layer, and Fact Explorer scans both roots. `FORM_BUILDER_EXTRA_APPS_DIRS` (set to
`/apps-external` in `docker-compose.override.yml`) is what names the second one; `appsDirs()` in
`packages/fact-explorer/scripts/build-registry.mjs` is where the two are joined, with the apps
directory first so it stays authoritative on a duplicate id.

## Writing one

Normally you do not. A generated application's `make up` writes its own fragment here (see
`scripts/register-with-taxpert.sh` in that repo) and recreates the `fact-explorer` container so it
re-reads the directory. Hand-write one only for an application that predates that script, or delete
one whose repository has moved or been thrown away — a fragment naming a path that no longer exists
fails `docker compose up` for the whole stack, which is the one sharp edge of this mechanism.

```bash
rm docker-compose.apps.d/my-application.yml   # unregister
```

## Why a restart is needed after adding one

Fact Explorer reads the application list twice, both at container start: `npm run make-fgm` calls
`buildRegistryFile()` to write `public/data/apps.json`, and `vite.config.js` builds its proxy table
from the descriptors it finds. Neither is watched, so a fragment added while the stack is up has no
effect until the container is recreated. That is what the registration script does for you.
